## 4. Related work

相关工作集中在独立的第 2 节 p.3，分成三个小节，约 420 词、占正文论证词约 8.3%，没有移到 appendix。三簇均按“已有工作做到哪里、缺哪一个评价维度、SwingArena 将缺口变成 CI arena”的顺序推进。

1. **Real-world software engineering benchmarks（143 词）**：以 SWE-Bench 为最近邻，指出其 Python 范围、unit-test-only 和 noisy/weakly aligned tests；再把 Multi-SWE-Bench、SWE-bench+、SWE-PolyBench 等多语言扩展与手动 Docker/缺少严格 CI 联系起来。动作是 `taxonomy → nearest_neighbor_contrast → gap_creation`（p.3，anchor “How to integrate real-world workflows…”）。
2. **Code evaluation（123 词）**：按 function-level correctness 与 repo-level effects 分类，承认既有 assessment strategies 的基础，同时指出缺少嵌入真实 CI、观察 build stability/regression 和 adversarial test agent 的能力。动作是 `credit_or_foundation → limitation_of_prior → gap_creation`（p.3，anchor “overlook repo-level effects”）。
3. **Retrieval-augmented generation（154 词）**：从 code graph/AST 的结构化路线对比 BM25 的 lexical 路线，说明 static analysis/fine-grained structure 的缺口；最后主动把 RACG 定位为 robust、language-agnostic、reproducible baseline，并承认 language-specific retrieval 是 future direction。动作是 `taxonomy → nearest_neighbor_contrast → positioning_only → scope_boundary`（p.3，anchor “strong, reproducible baseline”）。

引用簇约为 3 个主题簇、每簇含多篇引用；引用随后在方法中再次承担选择依据（BM25/CodeBERT/AST 与 long-context，p.6），在实验中承担 baseline 身份（p.7），但没有在结果中逐项与 SWE-Bench 或其他 benchmark 做同任务量化比较。相关工作没有复述完整的 Arena 机制，因而定位效率较好；真正的风险是“真实/专业/严格”等价值词多于可比的外部基线。

## 5. 方法、理论与算法

### 方法最小逻辑单元

方法动作序列为：

`setup_notation → state_problem → define_component → explain_mechanism → give_intuition → instantiate_algorithm → connect_to_prediction → connect_to_experiment`

具体推进如下：

- **Data Construction（p.4）**：先列 Repository Mining、CI Test Filtering、LLM Filtering、Expert Filtering 四阶段；GitHub API 按 popularity/star count 筛 repo，抽取 issue–PR、patch、test、base commit SHA、timestamp、CI list；保留 CI 全通过实例，再用 Grok-3-beta 给 clarity/difficulty 理由，最后由专家校准。Figure 1 把四阶段画成从 repo 到 filtered instances 的 pipeline。
- **Arena（p.4–6）**：先说明共享代码库和相同 task description，再把一轮 patch/test/CI/scoring 定义为 battle。submitter 修 bug，reviewer 生成能击穿 patch 的 test；golden human patch 作为正确性参照。执行端复制 GitHub Actions/Travis CI，使用 container、Rust cargo 与 Docker 配置；结果汇总为 CI logs 和 model outputs。
- **评分与门控（p.5–6）**：patch 通过全部检查得 +1，任一失败为 -1；reviewer 的 test 击穿 submitter 得 +1，击穿 golden patch 则 -1。reviewer test 还必须在 golden patch 上 compile/pass、不改 production code/已有 tests、限制新文件行数、避免 nondeterminism 并过 lint/style，否则自动拒绝并失去 reward（p.6，Appendix D 被调用）。
- **RACG（p.6–7）**：先用 BM25 做 file-level coarse retrieval，取 top-k files；CodeChunker 按 function/class/block 做多语言 syntax-aware chunking，解析不可用时按语言使用 regex heuristic；CodeReranker 用 CodeBERT 的 dense vector/cosine similarity，再加 definition-over-usage tie break、邻近 chunk proximity bias、跨文件去重；Token Budget-Aware Context Management 按剩余预算调节 chunk 粒度并附 file/symbol/line metadata。
- **方差控制（p.6）**：固定 system/user prompt、round/retry 上限、主实验 temperature=0、scaling-law temperature=0.25、act+pinned images 和 random seeds。p.7 又复述一次同一 Battle Protocol，形成方法解释和实验配置的重复。

### 公式、理论和伪代码

正文只有两个 displayed equation 区块，均未编号。它们是 `Best@k`（p.7）和同时定义 `SPR`/`RPR` 的 task-level average（p.7）。由公式可恢复的含义是，Best@k 按 task 计“至少一个成功尝试”；SPR 对每 task 的 submitter-side checks 通过比例先求平均；RPR 对 reviewer-generated tests 在 golden patch 上通过比例先求平均。PDF 中没有 theorem、lemma、proposition、corollary、proof、复杂度界或 formal optimization objective；因此理论模块为 `not_present`。RACG 的 determinism 是设计声明，属于 reproducibility/diagnostic，而非证明性质。

Algorithm 1（p.18，浮在 Appendix C.1 与 D 标题之前）给出 30 行高层流程：初始化 agents → 加载 issue/code → 生成并验证 patch → 生成并验证 test → 联合 CI → 加分 → reverse roles → aggregate scores。它覆盖了 control flow 粒度，未给出 retrieval 内循环、retry 规则、golden-test rejection 的完整分支，因此不能独立复现所有评分边界。

## 7. 结果、统计与可视化

### 主要结果清单

1. **Table 1（p.8，proprietary self/cross-play）**：16 个 matchup 给 RPR、SPR、Win Rate。self-play Win Rate 为 GPT-4o 0.97、Claude 1.00、Gemini 0.91、DeepSeek 0.96；cross-play 大多 0.89–1.00。作者把高 self-play 解读为 patch/test 的 internal alignment，并指出 reviewer 会造成轻微 asymmetry。聚合是按 task 的 check fraction，再在 battle/round 上汇总；没有 task counts、区间或检验。Win Rate 的弱 reviewer 解释在 p.7 已明确提示，因而作者至少保留了不利解释。
2. **GPT-4o 与可靠性叙述（p.8）**：GPT-4o 作为 submitter 对所有 reviewer 的 Win Rate ≥0.90，被归因为 aggressive patch generation；作者同时用较低/波动的 RPR/SPR 解释 correctness 不稳定。DeepSeek 与 Gemini 的 CI pass rates 最高可到 0.66/0.64，被归因为 reliability。该叙述没有 model-level uncertainty 或 matched difficulty 分层。
3. **Table 2（p.8–9，Best@3）**：平均分 DeepSeek 0.59，Gemini/GPT-4o 各 0.57，Claude 0.55；C++ 对四模型为 0.64、0.64、0.63、0.63，Rust/Python 通常较低；DeepSeek 的 Rust 0.58、Go 0.61 是其跨语言亮点。统计是每 task 的“3 次中至少一次成功”比例，无误差表达。
4. **Figure 3（p.9，Best@k）**：Qwen2.5-Coder-7B-Instruct self-play 在 temperature 0.25 下独立尝试，submitter/reviewer 曲线约从 k=2 的 0.43/0.45 上升到 k=16 的 0.69/0.70。图是两条带点曲线，没有 seed band；Appendix C 另报 k=1,3,5 的三 seed median std <0.02。
5. **Table 3（p.9，RACG on/off）**：C++ Best@3/Win Rate 从 0.38/0.77 到 0.42/0.84；Python 从 0.44/0.71 到 0.46/0.84；Rust 从 0.49/0.72 到 0.58/0.75；Go 从 0.37/0.71 到 0.45/0.80。方向支持 RACG，但没有按 task 配对差、seed 或显著性。
6. **Table 3 retrieval baselines（p.9）**：BM25 为 0.38/0.62，Top-2 Related 0.42/0.69，Top-10 0.43/0.72，Top-20 0.43/0.73（Best@3/Win Rate）。作者把 Top-20 相对 BM25 的 Win Rate +0.11 作为 context/retrieval 对照，但 Related 的构造细节很少。
7. **Table 5（p.17）与重复的 Table 6（p.19）**：正确 patch file 的 hit rate，BM25 Top-2/10/20 为 0.182/0.207/0.195，Block 为 0.207/0.341/0.329，Function 为 0.277/0.371/0.368，Class 为 0.363/0.487/0.461。Class Top-10 相对 BM25 超过两倍；作者解释为结构线索更强但可能超过 context window，最终选 block-level reranker。Table 6 与 Table 5 数值相同，属于重复而非新的独立样本。
8. **Appendix C 的稳定性与 reviewer effect（p.17）**：3 seeds 的 Best@k variance median std <0.02 且随 k 增大下降；Gemini/DeepSeek 的 cross-play median ΔSPR 为 −0.02 到 0.01，GPT-4o tails 更宽。作者将其与 GPT-4o 对 style/format 更宽松、patch 更激进的 qualitative observation 联系起来；没有给完整分布或 task-level denominators。
9. **Failure typology（p.17–18）**：随机、按语言分层检查 100 个 failed trials，F1 cross-file incomplete patching 31%，F2 fragile/flaky test 19%，F3 style/security gate 24%，F4 retrieval locus mismatch 26%。进一步给出 F1 patch complexity Spearman ρ=0.67、F4 repository age ρ=0.58；F2 在 Python/Go 为 23%/21%，C++/Rust 为 15%/17%；高-security repo 的 F3 “up to 35%”。这些是人工分类与相关性描述，没有 p-value 或区间。
10. **Model-specific profiles（p.18）**：GPT-4o cross-file failure 38%，Claude-3.5 style violation 28%，DeepSeek context-retrieval failure 32%，Gemini concurrent-programming F2 25%。作者据此提出 architectural reasoning、semantic code understanding 与 non-functional requirements 三个改进方向；分母和模型间任务匹配没有展开。
11. **Appendix A Table 4（p.14，open-source）**：Qwen/Seed 8B、Qwen 14B/DeepSeek Lite 16B 的 RPR、SPR、Win Rate 约为 0.48–0.62、0.87–0.95。该表扩展了模型覆盖，但未在正文重新解释其 ranking 或与 proprietary 表做同一口径的不确定性比较。
12. **数据特征（p.14–16）**：Figure 4 用蓝色深浅编码 request tokens、柱高编码 response tokens；Figure 5 给 clarity/difficulty pie charts；Figure 6 给四语言 problem/patch length histograms；Figure 7 给均值。文本报告 Go 286.7/287.6、Python 2,369.9/852.6、C++ 205.4/631.2、Rust 216.1/1,059.9（problem/patch tokens），20-file context 均值为 Go 8,232、Python 29,258、C++ 54,483、Rust 36,875。数据用于说明 code context 才是 token bottleneck，没有把它们作为模型 efficacy 的主判据。
13. **Appendix I step example（p.25–29）**：给出 nonexistent-model issue、patch/test JSON、reviewer output 和 act CI log；最后显示 Go setup、generate clean、go test 均成功。它是 qualitative/reproducibility example，不是独立成功率；示例中 top retrieved chunk 为 `stb_image.h`，与 issue 的 `server/...` 路径不一致，反而具体呈现了 retrieval/schema/CI 之间的潜在断点。

### 统计和图表的综合判断

聚合单位主要是 task，SPR/RPR 是“每 task 内的 check fraction，再对 task 平均”；Best@k 是 task solved fraction；Win Rate 又按 battle 的 cumulative rounds 叙述。论文没有把每个 matchup 的 task 数、每 task check 数、failed API calls 数或 paired task-level difference 展开。主表只给 point estimate；唯一的跨 seed 不确定性是 Appendix C 的 median standard deviation，未进入 Figure 3/Table 1–3。没有 hypothesis test、multiple-comparison adjustment、bootstrap 或 Bayesian model。图注能说明编码通道和总体目的，但 Figure 3 缺样本数/seed，Figure 4–7 缺原始 n，Table 5/6 的重复和编号错误会增加读者核对成本。

显著性与实质意义没有被分开检验。作者用 0.11 Win Rate 差、7–15 points localization gain、12–18% token footprint reduction 和相关系数支持方向，但没有说明这些差异的 sampling variation。另有一个文字与图形冲突。Figure 5 的 clarity 饼图视觉值为 Go 94.7%、Python 93.7%、C++ 97.1%、Rust 94.2%，p.15 文字却按 Python 97.1%、Go 93.7%、C++ 94.2%、Rust 94.7% 叙述；该排列应当以图和原始统计重新核对。

## 9. 结论、限制与闭环

结论 p.10 只有一段，动作是 `重述问题 → 重述方法 → 回收结果 → 影响`：SwingArena 评估 program repair/test generation；submitter–reviewer 多语言互动形成 holistic benchmark；RACG 合并 static analysis、dense retrieval 和 token-aware packing；四语言实验揭示 patch assertiveness、correctness、review strictness 的 trade-off。结论没有新数字，也没有回收 Appendix F 的 15% retrieval-attributed failure、compute overhead 或 negative impact。

### 主要限制

- **RACG 与窗口**：BM25、chunking、CodeBERT reranking 的质量决定上下文；固定 5 files/16 chunks 在超过 5 文件或 lexical association 弱的 issue 上会漏信息。作者在 p.20 归因约 15% failure cases 于 retrieval，且 F4 占人工失败样本 26%（p.17、p.20）。
- **成本与规模**：`act` 驱动的迭代 CI 加 RACG 比 HumanEval/MBPP 更耗时、耗资源；没有 wall-clock、硬件或成本曲线（p.20）。
- **外部效度**：popular repositories、CI 全通过和 clarity/difficulty filtering 使数据偏向已有社区验证、可执行、较清晰的 issue；只覆盖四种语言和 400 个主评估实例（p.4、p.7）。
- **评分边界**：reviewer 的 reward 同时依赖击穿 submitter 和不击穿 golden patch；Algorithm 1 的 `test fails to expose meaningful flaw` 分支没有重现文字版 golden-fail 处罚（p.5–6、p.18）。
- **证据自足性**：主表没有 n、区间、每轮 outcome、每模型 API/hardware 细节；Appendix I 的 CI success 只能证明示例 pipeline 跑通，不能证明 test 的语义有效性（p.7–8、p.25–29）。
- **未明示的缺口**：没有 human reviewer baseline、matched static benchmark、train/test contamination audit 或独立安全审计。论文没有把这些缺口作为主文 limitation 句明确列出；结论也没有范围收缩（p.10、p.19–20）。

## 11. 不利信息呈现与叙事风险

以下只记录版面和文本可验证策略，不推断作者动机：

1. **后置到 appendix**：p.10 以一句话把 data/failure analysis 转到 Appendix C；完整 F1–F4、15% retrieval attribution、3-seed variance 和 model profile 均出现在 p.17–18。主文先完成“nuanced insights”叙述，再给失败机制。
2. **聚合遮蔽异质性**：SPR/RPR 先对 task 内 checks 求比例再平均，Win Rate 还以 cumulative rounds 表达；表格没有 task/check/battle 分母（p.7–8）。这使跨 matchup 的数字易读，但读者无法从表中判断任务难度或检查数量的差异。
3. **点估计优先**：Table 1–3、Table 4–6 和 Figure 3 没有 uncertainty band；只在 appendix 用 median std <0.02 概括稳定性（p.8–9、p.17）。
4. **正面指标先行、反向解释随后**：Table 1 先突出极高 Win Rate，随后 p.7 的定义才提醒 high Win Rate 也可能代表 weak reviewer tests；作者确实提供了 caveat，但读者需要回读指标定义。
5. **交叉引用/编号成本**：p.9 的 patch localization 写成 Table 6，p.17 是 Table 5，p.19 重复 Table 6；p.14 “Appendix 5” 与 A–I 编号体系不一致。它们是可见的导航问题，并非新的实验结论。
6. **格式契约不一致**：p.7 说所有 model outputs 遵循 structured JSON schema；H.1 的 system prompt 又要求只输出 fixed code/test code；p.25–28 示例则包含 reasoning_trace、code_edits/test_cases 的 JSON。评测实现者需要自行决定哪个 contract 生效。
7. **示例成功与语义质量分离**：Appendix I 的 act 日志显示 Go `go test` success，但样例 top retrieved chunk 是与 issue 路径不一致的 `stb_image.h`，reviewer test 也展示了 schema/code plausibility 的疑问；CI 的 green 状态不能单独等同于 reviewer test 的有效性（p.25–29）。
8. **图文数字错位**：Figure 5 clarity 百分比与 p.15 文字发生语言标签轮换；这会把数据分布主张变成需要二次核对的证据，而非直接闭环。

## 13. 最终判断

1. **单一主线**：论文把“GitHub issue 的 patch 是否通过一次固定测试”改写为“submitter 生成 patch、reviewer 生成对抗 test、双方在真实 CI 中轮换并计分”，RACG 是把多文件多语言 code context 稳定送入这条循环的配套层（p.2、p.4–7）。
2. **正文保留的决策关键内容**：三类既有 blind spots、battle 的角色/评分/golden patch、Docker/CI gates、RACG 四组件、5-file/16-chunk 配置、temperature/round 设置、Best@k/SPR/RPR/Win Rate 定义，以及 Table 1–3 的主方向（p.2、p.5–9）。
3. **迁移到 appendix 的内容与代价**：open-source 表、数据分布、失败/稳定性、annotator、限制、prompt、JSON 和 CI 示例均在 p.14–29；主文因而保持短而顺，但没有独立复核 failure denominator、output contract、硬件/API 和 retrieval 的完整机制。
4. **最有效的模式**：Figure 2 的双角色流程图与文字评分规则相互补足；Table 3 把 RACG on/off 和 retrieval baseline 放在同一表；RPR/SPR/Win Rate 并列且主动提示 Win Rate 可能被弱 reviewer test 抬高（p.5、p.7、p.9）。
5. **最大缺口**：结果是点估计的 descriptive aggregate，没有 human/static matched comparator、完整分母或 uncertainty；protocol 的文字/Algorithm/JSON contract 互有缺口，Table 5/6、Appendix 5 和 Figure 5 产生导航或数字核对成本（p.7–9、p.14–19、p.21–29）。
6. **可迁移规则**：交互式 benchmark 必须把每个角色的输入、输出、golden/reference、reject gate、计分转移和 reverse-role 聚合写成同一个可执行矩阵，并让每个矩阵分支对应一个结果表；扩展分布可以放 appendix，决定结论的分母、失败判定和不确定性应留在正文。
7. **适用边界**：这条规则适合 CI、agent battle 或昂贵 evaluator loop；当任务没有 golden patch、可运行 CI 或可校验 reviewer test 时，Win Rate/role-switch evidence 不能直接替代真实软件质量、人类评审或外部效度验证。
