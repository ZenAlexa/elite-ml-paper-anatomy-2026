## 5. Related work

相关工作是独立 §2，跨物理页 2–3，约 510 词，占正文 p. 1–10 提取词数约 8%。它由两个长段组成，先按应用与 paradigm 组织，再按 meta-evaluation 目标组织；每段末尾把缺口收回 WebDevJudge。

1. **LLM-as-a-Judge（p. 2–3, §2）**：先列 question answering、data filtering、trajectory evaluation 的应用（`taxonomy`），再从 conventional LLM-as-a-Judge 过渡到 Agent-as-a-Judge（`chronology`）。随后把 position／verbosity bias、rubric 成本、对 final outcome 的过度依赖作为 prior limitations，并以“benchmark open-ended web development”定位最近邻差异。锚点为“position bias … and verbosity preference may skew results”。该段的比较维度是任务形态、评测输入和 agentic capability，而非逐篇效果数字。
2. **Meta Evaluation（p. 3, §2）**：按“preference alignment”与“correct task outcome”分两类（`taxonomy`），将 MT-bench／LLMEval 与 LLM-Bar／JudgeBench 对照为文本任务，将 AgentRewardBench 与 ArtifactsBench 对照为 trajectory／dynamic visual tasks（`nearest_neighbor_contrast`）。最后指出已有工作缺少由实时用户输入驱动的环境变化，直接引向 WebDevJudge。锚点为“mainly focus on text-based tasks without complex environments”。

相关工作没有重新讲 rubric tree 的实现；rubric 仅作为 prior work 与本方法的定位线索，真正的树结构、叶节点和聚合在 §3 出现。引用在 §4 继续承担 paradigm、bias、agent failure 与 multimodal observation 的论证角色，发挥连续论证作用，而非一次性 citation dump。

## 6. 方法推进与理论边界

### 6.1 WebDevJudge 方法单元

方法从任务形式化开始，随后依次过滤数据、重做标签、验证 rubric、给出分布。最小逻辑单元和转移如下：

1. `state_problem → define_component`（p. 4, §3）：把一条实例定义为 `(Q, W_a, W_b, l_p)`，其中 `Q` 是 query，`W_a/W_b` 是两个模型的 web implementation，`l_p ∈ {a,b,tie}` 是偏好标签；观察形式可为 code、screenshot 或 interaction trajectory。锚点为“Each instance is represented as a quadruple”。
2. `instantiate_algorithm`（p. 4, §3.1）：从 `webdev-arena-preference-10k` 的 10,501 条 query／成对 code 出发，执行 query-based 与 environment-based 两阶段过滤。锚点为“We apply a two-stage filtering process”。
3. `define_component`（p. 4, §3.1）：query filter 删除极短／逐字重复 query，再按 safety、clarity、feasibility 筛选。锚点为“Safety … Clarity … Feasibility”。
4. `explain_mechanism`（p. 4, §3.1）：统一环境部署每个实现，丢弃 deployment／niche dependency 失败，并用初始 screenshot 的 MLLM 检查空白页或 intrinsic error。锚点为“capture initial screenshots of each rendered webpage”。
5. `derive`（p. 4–5, §3.2）：先对 100 个实例重标，显示原始偏好存在主观性；再引入 query-based rubric tree，沿 intention、static quality、dynamic behavior 组织层级。锚点为“organized along three core dimensions”。
6. `define_component → connect_to_prediction`（p. 4, §3.2）：每个叶节点是 binary test，向上聚合为 root holistic score，同时保留 leaf-level pass rate 作为 diagnosis。锚点为“Each leaf node corresponds to a binary test”。
7. `instantiate_algorithm → connect_to_experiment`（p. 5, §3.2）：用 few-shot LLM generation 自动生成树；第三位 annotator 与 human-written rubric 对照，随后由两位有 software engineering 背景的 expert 标注剩余数据。锚点为“Final inter-annotator agreement on a sampled subset reaches 89.7%”。
8. `summarize`（p. 5, §3.3）：最终保留 654 instances，标签为 a=269、b=276、tie=109；按三大类别统计 query coverage。锚点为“The final benchmark consists of 654 instances”。

### 6.2 方法组件解决的问题

- **双阶段过滤**降低原始 webdev-arena 数据中的重复、危险／不清晰 query 和不可部署实现风险；Appendix B 把每个阶段的 before／after 数量补全为 10,501 → 6,730 → 2,460 → 1,814 → 1,713 → 700 → 654（p. 16, Table 8）。
- **Rubric tree**把开放式高层意图变成可验证 binary leaves，解决直接偏好标签主观性；但生成树的粒度仍随 query 明确度变化（p. 18–20, Appendix B；“rubrics … can be overly fine-grained”）。
- **多模态／交互表示**让同一 paired instance 可在 code、screenshot、trajectory 三种观察条件下评测（p. 4, §3；Fig. 1）。
- **WebDevJudge-Unit**把“能否完成一个具体操作”单独拆成 502 个 feasibility tasks，作为 preference agreement 之外的诊断边界（p. 9, §4.3；p. 26, Appendix D）。

### 6.3 理论对象与公式

论文没有 theorem、lemma、proposition、corollary、proof、复杂度定理或可证明泛化保证。两条 display equation 都是方法／实验规则：

- **Eq. (1), p. 6, §4.1**：`Query → Plan with test cases → Results → Judge` 的 planner–executor–summarizer 流程；作用是把 agentic workflow 的阶段边界显式化。锚点为“Planner … Executor … Summarizer”。
- **Eq. (2), p. 10, §4.3**：`Res_dynamic = Agent ∨ LLM`；作用是把 agent 的 precision 与 LLM 的 recall 互补关系实例化为 gated ensemble，而非理论保证。锚点为“Agent provides high-precision filtering … LLMs ensure higher recall”。

因此 theory 模块为 `not_present`；方法推进主要是 `state_problem → define_component → explain_mechanism → derive → instantiate_algorithm → connect_to_experiment`，没有独立的理论闭环。

## 7. 实验设计

### 7.1 研究问题与控制结构

§4 开头预先列出两个 RQ。LLM-as-a-judge 能否替代复杂 web development 中的人类偏好，以及不同 settings／strategies 如何影响 agreement rate（p. 5, §4；锚点：“focusing on the following research questions”）。实验先做主 benchmark performance，再控制 guidance 与 observation form，最后做 bias、equivalence、feasibility 的 error analysis。顺序与引言的 benchmark → performance gap → failure modes 一一对应。

### 7.2 数据、任务、评估对象

- **数据**：654 个 paired web implementations；query 类别为 Digital Design 34.0%、Game and App Development 34.4%、Web and Specialized Technologies 31.6%（p. 5, §3.3, Table 2）。
- **人类对照**：human pairwise average agreement 84.56%，三类分别为 84.23、83.11、86.47（p. 6, Table 3）。正文称 expert human judgments；没有给出 participant 数量之外的 demographic 或 adjudication 细节。
- **Vanilla evaluators**：表 3 覆盖 OpenAI、Anthropic、Google、Qwen、DeepSeek、Moonshot、ZAI 的非 reasoning／reasoning 模型；具体包括 GPT-4.1、GPT-4o、Qwen-2.5-VL-72B、Gemini-2.5-flash-lite、DeepSeek-V3-0324、Kimi-K2、Qwen3 系列、Gemma-3、Claude-4／3.7、Gemini-2.5-pro、GLM-4.5、DeepSeek-R1 等（p. 6, Table 3）。
- **Agentic evaluator**：UI-TARS-1.5 作为 executor；planner 使用 LLM-generated rubric tree，summarizer 汇总执行结果（p. 6, §4.1；Eq. 1）。
- **输入观察**：single grading 给 query、code、criteria，MLLM 加初始 screenshot；pairwise 给 query、两段 code、criteria 和两张 screenshot（适用时）（p. 6, §4.1）。

### 7.3 评测协议、指标与复现粒度

- **Pairwise**：直接比较两段实现，或分别打分后比较总分；preference 为 a、b 或 tie。
- **Single answer**：单独给每个实现打分／pass rate，再比较结果。
- **Likert**：Functionality、UI Quality、Code Quality、Interactivity 四个维度，子维度为 5-point（1–5）量表；Appendix C 列出 core functionality、content completeness、corner cases、error handling、visual consistency、responsive layout、aesthetics、readability、modularity、scalability、interactive effectiveness／logical correctness／accessibility（p. 6, §4.1；p. 22, Appendix C）。pairwise 的 score difference **超过 1** 才判胜，否则为 tie（p. 21, Appendix C）。
- **Rubric**：leaf binary pass／fail；intention、static、dynamic 三维 pass／win rate 以权重 1、3、2 聚合；single 与 pairwise 的聚合定义分别在 Appendix C（p. 21）。
- **Direct**：不给显式 criteria，直接输出 `W_a`、`W_b` 或 tie（p. 21, Appendix C）。
- **Agent step budget**：Static 最多 6 步；Dynamic basic 最多 5 步、complex 最多 15 步；Intention 最多 15 步（p. 23, Table 11）。动作空间是 UI-TARS 官方 action space，经 pyautogui 执行。
- **实现／温度**：开源模型用 vLLM 或 SGLang；商业模型走 Azure、Vertex AI API；非 reasoning 模型 temperature=0.0，reasoning 模型按各自设置（p. 21, Appendix C）。
- **未提供的设计量**：论文没有报告每项主结果的随机种子、训练预算、硬件规格、样本级数据泄漏检查、置信区间／bootstrap、显著性检验或失败判定阈值之外的统计检验。它提供了 deployment 的 non-200／screenshot 过滤规则、Likert 的 score-difference threshold 以及 agent max steps，但没有把这些写成统一 failure criterion。

## 8. 结果、统计与可视化

Agreement rate 是主要决策量；作者按 dataset category、model、paradigm 聚合，没有报告区间或假设检验。人类与模型的比较因此应读作有限 benchmark 上的 proportion agreement，而非带不确定性的总体估计。

### 8.1 主结果（Table 3，p. 6；分析 p. 7）

1. **低于人类**：GPT-4.1 pairwise average 70.34%，human pairwise average 84.56%，差 14.22 个百分点；正文将其概括为约 15% discrepancy。GPT-4.1 的 single average 为 60.86%。锚点为“top-performing evaluator, GPT-4.1 under the pairwise paradigm”。
2. **pairwise 优于 single**：作者称全体平均提升超过 8.0%；GPT-4.1 的 70.34–60.86=9.48 个百分点，Claude-4-Sonnet 为 70.18–59.17=11.01 个百分点。作者把差异与 relative discrimination 和 absolute calibration 负担联系起来，未给检验统计量（p. 7, §4.1）。
3. **模型上限**：正文称更大／更强模型出现 diminishing returns，约在 70% 附近平台化；这是跨模型表格的解释，不是拟合出的 scaling law（p. 7）。
4. **Agentic rubric**：intention、static、dynamic、combined 的全体 single average 分别为 39.45、51.07、55.66、60.55；combined 高于三项单维，但仍低于最好 vanilla reasoning model 的 single average 63.91（Claude-3.7-Sonnet），支持“多阶段错误抵消收益”的定性判断（p. 6–7, Table 3）。
5. **类别异质性**：GPT-4.1 pairwise 在 Digital Design、Game & App、Web & Special 分别为 70.72、73.33、66.67；human 为 84.23、83.11、86.47。表中保留了类别列，但没有 seed／task-level dispersion（p. 6, Table 3）。

统计处理：agreement rate 的分母是相应类别／范式中的实例数；tie 作为第三个标签参与 agreement。没有 CI、显著性测试、bootstrap、回归或 Bayesian 分析。图表的注释能独立说明指标和比较对象，但不能独立恢复样本量或不确定性。

### 8.2 Guidance 与 observation（Fig. 3、Table 4，p. 7–8）

- **Guidance**。Figure 3 比较 Direct、Likert、Rubric。六个模型的 pairwise Direct 分数与 rubric／Likert 接近。GPT-4.1 为 68.7（Direct）、70.0（Rubric）、70.3（Likert）；GLM-4.5 为 69.7、68.2、68.7。single 下 Rubric 明显高于 Likert。GPT-4.1 为 65.6 对 60.9，DeepSeek-R1 为 63.5 对 54.6。作者据此把 pairwise 的相对偏好视为较内化能力，把 binary rubric 视为 absolute grading 中更可用的协议（p. 8, §4.2；“external guidance provides only marginal benefits”）。
- **Observation modality**：Table 4 以 Image Only、Code Only、Both 做 MLLM 对照。GPT-4.1 pairwise 为 60.55、69.57、70.34；Claude-4-Sonnet 为 59.48、67.58、70.18。相对 Both，缺 code 的 Image Only 下降 9.79／10.70 个百分点，缺 image 的 Code Only 只下降 0.77／2.60；Gemini-2.5-pro 与 Qwen-2.5-VL 在 single 的 Image Only 反而略升，故“code 是最关键 modality”是总体趋势而非每个格子的单调规律（p. 8, Table 4）。

### 8.3 Error analysis（Table 5、Fig. 4、Table 6–7，p. 8–10）

- **Position bias（Table 5）**：Claude-4-Sonnet direct／Likert consistency 为 89.6／87.9，GPT-4.1 为 83.3／85.2，DeepSeek-V3 为 84.1／83.5；GPT-4.1 在 direct 下 second position 偏好 15.8%，first 0.9%，Likert 下为 11.8% 对 3.0%。原序与 swapped 序 agreement 差 `Δ AR` 最大为 Claude direct 0.61／Likert 1.53、GPT-4.1 0.30／1.07、DeepSeek direct 1.53／Likert 1.23。作者观察到不一致样本的 tie 比例没有高于 win/loss，因而不把 bias 只解释为 tie ambiguity（p. 9, §4.3；“instruction alone is insufficient”）。
- **Functional equivalence（Fig. 4）**：要求 “Demonstration” rating row，而页面以同功能的 “Presentation” row 实现；human 判 true，LLM 与 Agent 判 false。作者把它作为 literal wording 压过 underlying intent 的案例，未给出总体错误率（p. 9；“The webpage element for ‘Presentation’ serves the same purpose”）。
- **Feasibility／Unit（Table 6）**：502 tasks、105 queries；UI-TARS-1.5（trajectory）P/R/F1/Acc=82.4/70.3/75.8/75.1；GPT-4.1（code）=72.1/90.0/80.1/75.1；DeepSeek-V3（code）=69.6/93.5/79.8/73.7。模型 code-only 的 recall 高、precision 低，agent 的 precision 高、recall 低；作者将前者归因于缺少 execution grounding，后者归因于 navigation／state interpretation 失败（p. 9；“static code analysis lacks execution grounding”）。
- **Gated ensemble（Eq. 2、Table 7）**：GPT-4.1 由 65.0 提至 66.2，DeepSeek-V3-0324 由 66.3 提至 67.6；LLM 负责 intention/static，dynamic 取 `Agent ∨ LLM`。这是有限模型上的小幅 agreement 增益，论文没有拆解 OR gate 的 false-positive／false-negative 变化（p. 10, §4.3）。

## 13. 最终判断

1. **单一主线**：论文把“LLM judge 是否可靠”从静态、答案明确的文本评测推进到 web development 的动态开放式 preference meta-evaluation；query-grounded rubric tree 提供标签质量，code／screenshot／interactive environment 提供观察层，pairwise agreement 暴露能力上限，Unit／案例把上限拆成 bias、functional equivalence 和 feasibility verification 三个瓶颈。
2. **正文保留的决策关键内容**：benchmark 定义与过滤结果、rubric agreement、654／269／276／109 数据规模、pairwise／single 协议、模型主表、人类基线、modality、bias、Unit P/R/F1/Acc、ensemble 结果与结论边界。它们共同回答“测什么、怎样测、差距多大、哪里失败”。
3. **移入附录的细节及代价**：过滤 prompts、annotation guidelines、rubric tree prompt／统计、Likert 13 子标准、API／temperature／action space、Unit error taxonomy、swap／no-tie consistency、qualitative cases 与 LLM disclosure。迁移保持正文叙事紧凑，却让复现和评估范围判断依赖附录，尤其是 tie threshold、dimension weights 与 Unit label construction。
4. **最有效模式**：把开放式偏好拆为 query-grounded binary leaves，再用 Figure 1 的三栏 overview 将 data→annotation→judge 串联；主结果 Table 3 统一列出模型、类别、paradigm，Table 4／6／7 以对照矩阵呈现 modality、precision–recall 与 ensemble，Fig. 4／10／11 把抽象 failure mode 绑定到可检查案例。
5. **最大叙事缺口**：`agentic workflow suffers from compounding errors` 有流程图、总体分数和案例，但缺少 planner／executor／summarizer 的阶段级错误分解或删除组件对照；functional-equivalence 主要是案例证据；agreement 没有不确定性与 task-level 分散，因此约 15% gap 的总体边界较清楚，机制强度较弱。
6. **可迁移规则**：复杂开放式评测应同时报告相对偏好与可验证的原子任务，并把每个强主张绑定到独立的观测模态、标签构造和失败诊断；聚合 agreement 之后必须保留能区分 literal mismatch、execution failure 与真实质量差异的诊断层。
7. **适用边界**：该规则适合有交互状态、多个合理实现和可定义操作测试的 web／GUI／agent 任务；当任务没有可执行环境、没有可靠人类偏好或无法构造 query-grounded leaves 时，binary rubric 与 Agent∨LLM gate 不能直接转移为普遍可靠性保证。
