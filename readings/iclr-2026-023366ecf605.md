## 5. 方法与理论

### 5.1 最小逻辑单元与前文问题的对应

1. **`setup_notation`**：把 vulnerability 绑定到 program versions。漏洞存在于 pre-patch、完整 patch 后在 post-patch 解决；latest version 仍可能保留 zero-day。[p. 3–4，§3.1，“pre-patch version but is resolved”，`explicit`]
2. **`explain_mechanism`**：sanitizer 在潜在不安全位置插入 runtime checks，触发时主动 crash 并输出 error report，因此充当 vulnerability-detection oracle。[p. 4，`Sanitizers as Vulnerability Detection Oracle`，`explicit`]
3. **`credit_or_foundation`**：OSS-Fuzz 的持续 fuzzing、PoC、patch 监测构成历史数据源；ARVO 只提供 reusable Docker images，不定义 evaluation task/metric。[p. 4，`ARVO itself does not define any evaluation tasks or metrics`，`explicit`]
4. **`scope_boundary`**：范围锁定 sanitizer-detectable memory safety、主要 C/C++；作者承认这可能遗漏完整 vulnerability landscape，并把扩展放到 §6。[p. 4，`Scope, Rationale, and Limitations`，`explicit`]
5. **`state_problem`**：Level-1 输入为 vulnerability text description、pre-patch codebase 和 containerized pre-patch executable；输出是 agent 生成的 single raw-input PoC，可通过 `bash submit.sh` 迭代执行。[p. 4，`Task Input and Output`，`explicit`]
6. **`define_component`**：执行 oracle 要求 `(i)` pre-patch sanitizer crash 与 `(ii)` post-patch 无 sanitizer crash；instance success rate 是成功实例百分比，因而排除了只触发任意 crash 的宽松判定。[p. 4–5，`Execution-Based Evaluation Metrics`，`explicit`]
7. **`define_component`**：Level 0 去掉 text description，构成 exploratory/open-ended vulnerability discovery；它同时作为 §5 的 discovery setting。[p. 5，`Level 0`，`explicit`]
8. **`define_component`**：Level 1 是主 reproduction task；Level 2 在 Level 1 上加入 ground-truth PoC 的 crash stack trace；Level 3 再加入 patch diff 和 post-patch codebase。[p. 5，`Level 1`–`Level 3`，`explicit`]
9. **`derive`**：OSS-Fuzz 每日更新；作者在 fixed vulnerability 前一天的 commit 区间做 binary search，找出第一个使 PoC 不再触发的 patch commit。[p. 5，`Sourcing from OSS-Fuzz`，`explicit`]
10. **`define_component`**：从该 commit 得到 pre/post codebase、ground-truth PoC、ground-truth patch，并编译 sanitizer-enabled executables；再用 GPT-4.1 将 patch commit message 改写成 description。[p. 5，`benchmark elements`；p. 19–20，Figures 9–10，`explicit`]
11. **`explain_mechanism`**：质量管线过滤缺乏 location/root-cause 信息或一次修复多个 issue 的 commit；人工抽样 300 instances 评估过滤质量。[p. 5、20，`Quality Assurance`；`Human Verification`，`explicit`]
12. **`connect_to_experiment`**：重跑 ground-truth PoC，按 crash stack trace 排除重复 patch/executable；最终得到 1,507 instances、188 projects、28 crash types。[p. 6、17–18，`Validating reproducibility`；`Removing redundancy and ambiguity`，`explicit`]

动作转移序列为：`setup_notation → explain_mechanism → credit_or_foundation → scope_boundary → state_problem → define_component(levels) → derive(version boundary) → quality_assurance → connect_to_experiment`。方法图 Figure 2 将 Day 0/Day 1、patch range、Day n 的 binary-search 关系压缩到时间线，承担数据构造机制的核心解释。[p. 5，Figure 2，`layout_observation`]

### 5.2 形式化对象、假设、算法与理论库存

- **形式化对象首次出现**：pre-patch/post-patch program versions 与 patch completeness 在 §3.1（p. 3–4）；text description、codebase、executable、raw-input PoC 在 §3.2（p. 4）；success rate 在 p. 5；Level 0–3 在 p. 5；binary-search patch boundary 在 p. 5。
- **隐含操作假设**：sanitizer crash 足以作为指定 vulnerability class 的 observable oracle；post-patch no-crash 能区分 target vulnerability reproduction 与其他 crash；OSS-Fuzz 的 ground-truth PoC 可复现。作者将这些作为执行设计陈述，未给出 formal theorem。[p. 4–6，`explicit`/`interpretation`]
- **公式**：正文没有 displayed equation、numbered equation 或公式总数可列项；数学符号只出现在 prose 的 `(i)/(ii)` 条件和 Appendix Table 9 的均值 `±` 中。
- **理论结果**：没有 theorem、lemma、proposition、corollary 或 proof；`theory` 模块为 `not_present`，不存在“保证 agent 成功”的理论链。[p. 1–46，`explicit`]
- **算法/伪代码**：没有 Algorithm 环境。binary search 只以文字和 Figure 2 描述，未提供伪代码、循环不变量或渐进复杂度。[p. 5，Figure 2 与 `performing a binary search`，`explicit`]

## 6. 实验设计、复现粒度与统计

### 6.1 研究问题与任务配置

论文没有预先列出编号化的 hypotheses；§4 用描述性标题组织问题：「Backbone LLMs Differ Significantly」「Thinking Mode Improves Success Rate」「Different Agents Show Distinctive Behaviors」「Limited Impact of Potential Data Contamination」「Richer Input Information Enhances Reproduction」「Challenges in Handling Longer PoCs」等。标题本身带方向性，但没有预注册阈值或停止规则。[p. 6–8，§4，`explicit`/`interpretation`]

- **数据集与时间**：最终 1,507 vulnerabilities，披露日期为 2017-01-01 至 2025-04-21；其中 1,368 来自 ARVO（截至 2024-07-31），另收集 139 个较新漏洞。[p. 6，`Benchmark Scale and Diversity`，`explicit`]
- **任务与 oracle**：默认 Level 1；生成 raw input；pre-patch crash 且 post-patch no crash 才算成功。[p. 4–6，`explicit`]
- **难度变量**：Level 0 只有 pre-patch codebase，Level 1 加 description，Level 2 加 error/stack trace，Level 3 再加 patch.diff 和 repo-fix codebase。等级为累积信息量设计，并非随机化单变量消融。[p. 5、21，`explicit`/`interpretation`]
- **LLM 比较**：11 个 LLM，分 general-purpose closed-source、general-purpose open-weight、SWE-bench-specialized 三组；名单和 checkpoint 见 Appendix C Table 6。[p. 6–7、22，`explicit`]
- **agent 比较**：OpenHands、Codex CLI、EnIGMA、Cybench；主 LLM 比较统一用 OpenHands，agent framework 比较统一用 GPT-4.1。[p. 6–7，`explicit`]
- **迭代与成本**：OpenHands/Codex/Cybench 最多 100 iterations；EnIGMA 使用 `ctf_pwn.yaml`、demonstrations removed、约 `$2.0`/task；full non-thinking evaluation 约 `$3,000` API credits；另提供随机 300-instance subset。[p. 6–7、21，`explicit`]
- **thinking 设置**：默认关闭 Qwen3-235B-A22B、Claude-3.7-Sonnet；o4-mini 用 medium reasoning；GPT-5 full comparison 用 minimal reasoning。thinking comparison 同为 100 iterations，但提高 thinking output token；Claude extended-thinking comparison 还关闭 tool use。[p. 7、21，`explicit`]
- **训练/优化预算**：论文做 evaluation，不做模型训练；训练预算对本设计 `not_applicable`。硬件、checkpoint、agent commit 在 Appendix C 给出。[p. 6–7、21–22，`explicit`]
- **硬件**：submission environment 为 2× AMD EPYC 9654 96-Core processors、1.5T RAM、约 10TB disk；agent 在同机运行并调用 vendor/self-hosted APIs；另报告 1,000 H100 GPU hours 的总资源投入。[p. 2、20–21，`explicit`]
- **随机种子/独立重复**：没有报告 headline success rate 的独立 rerun 次数、随机 seed、run-level dispersion 或 error bar；300 subset 的抽样方式称为 random，但未给 seed。该项 `not_present`。[p. 6–7、21，`interpretation`]

### 6.2 控制、污染、人工 audit 与统计层级

- **控制/匹配**：agent framework comparison 使用 GPT-4.1，约相同 `$2.0`/task 预算；LLM comparison 使用相同 OpenHands、最多 100 iterations。这个匹配减少 scaffold/budget 差异，但不同模型 token/reasoning 配置仍不完全相同。[p. 7，`Different Agents...`；p. 21，`Detailed Agent Settings`，`interpretation`]
- **数据污染**：按各模型 knowledge cutoff 将 vulnerability disclosure dates 切成 pre/post；仅选择 post-cutoff 超过 50 samples 的四模型，使用 Fisher’s exact test 与 two-proportion Z-test。p 值均大于 0.1。[p. 7–8，Table 2，`explicit`]
- **人工质量 audit**：300 stratified samples（150 retained、150 filtered），覆盖 96 projects 和全部 crash types；两位作者独立 review、裁决分歧，Cohen’s κ=`0.82 ± 0.03`；过滤样本 6/150 缺 locating information，对应约 96% precision，并发现 10 false negatives；审阅的 rephrasing 均保留 essential technical content。[p. 20，`Human Verification...`，`explicit`]
- **复现粒度**：正文保留 task、oracle、levels、模型/agent 主结果；Appendix C 提供过滤/rephrasing prompt、README、token/iteration、checkpoint、commit 和硬件。完整的 431-project list 跨 p. 21–23。[p. 19–23，`explicit`]
- **统计单位**：headline success rate 以 instance 为分母；Table 2 为 pre/post disclosure split 的成功数/样本数；balanced resampling 先在每个 project 或 crash type 内求 success rate，再跨单位平均；Table 8 按 crash type 直接给实例数和 success rate；Table 9 给 difficulty-level ratio 与 `grep/ls/find` 平均次数/失败次数。[p. 7–8、23–26，`explicit`]
- **不确定性表达**：Figure 3–7 主图没有 error bars；Table 2 报两种检验的 p 值；Cohen’s κ 有 `±0.03`；Table 9 的 `±` 未在正文/表注定义其构造。显著性、实质大小和机制证据因此分散在不同对象中。[p. 8、20、26，`layout_observation`/`interpretation`]

### 7.2 统计解释边界

核心分母主要是 task instance；项目/crash-type balanced analysis 先在单位内聚合，再平均。Table 2 的 Fisher/Z-test 是论文唯一显式的 inferential comparison；论文没有报告 bootstrap、Bayesian analysis、regression、correlation 或 effect-size interval。Figure 3–7 没有误差表达，Table 9 的 `±` 没有定义。因此可以复述作者的「p 值未超过显著性阈值」判断，但不能把它升级为污染效应为零或各配置稳定可复现。[p. 8、23–26，`explicit`/`interpretation`]

结果的实质意义和机制证据被分开：success-rate figures 给能力差异，Figure 8 和 Appendix F 给 agent 操作机制，post-patch crash/zero-day workflow 给现实 impact。该组合支持论文的单一叙事，但 proxy claim 仍需要跨更多模型/任务的校准。[p. 9–10，`interpretation`]

## 9. 结论、限制与闭环

### 9.1 结论逐段动作

- **重述问题/方法**：CyberGym 是面向 AI agent cybersecurity capability 的 realistic、large-scale benchmark；1,507 instances 覆盖 188 open-source projects，形成 difficulty ladder。[p. 10，§6，`explicit`]
- **回收实验**：4 agent frameworks、11 LLMs；top combination 的 success rate 为 22.0%，并揭示短 PoC/较少 reasoning steps 和 complementary behavior。[p. 10，§6，`explicit`]
- **回收 impact**：incomplete security patches 与 34 new zero-day vulnerabilities，将 benchmark 延伸为现实 security impact。[p. 10，§6，`explicit`]
- **影响/未来**：贡献 broader AI safety landscape；future work 扩展到 logic/cryptographic flaws、web/mobile、多语言、patching/exploitation 与更细粒度 oracle，并改进 long-context、ensemble、security tools 和 tool use。[p. 10，`Future Work...`，`explicit`]

结论没有引入超出 §5 的新数字；它将摘要的约 20% 改成 22.0% 的 best setting，并把“reliable proxy”留在 §5，不在结尾额外证明。[p. 10，`explicit`]

## 14. 最终判断

1. **单一主线**：通过 OSS-Fuzz 的真实历史漏洞、pre/post sanitizer execution oracle 和自动/人工质量管线，把 PoC reproduction 做成 1,507-instance benchmark；模型/agent 结果揭示难度与互补性，post-patch replay 与 Level-0 搜索把评测延伸到 incomplete patch 和 zero-day discovery。[p. 4–10，`interpretation`]
2. **正文保留的决策关键内容**：任务输入/输出、双版本 success criterion、Level 0–3、数据规模、4 agent/11 LLM、Figure 3–7 的核心比较、Figure 8 成功机制 trace 和 §5 的 discovery pipeline；这些足以判断“测什么、如何判定、性能多难、为何有现实外溢”。[p. 4–10，`explicit`/`interpretation`]
3. **移入附录的内容及自足性**：prompts、README、hardware、checkpoint/commit、全项目/ crash-type 表、cutoff/重采样、failure ratios、长 trace 和 GDAL/zero-day 摘要移入 p. 16–46；benchmark headline 仍可读，但复现实验配置、失败分母和现实 impact 逐案证据需要附录，故 audit cost 上升。[p. 16–46，`interpretation`]
4. **最有效的模式**：Figure 1 的输入→oracle→impact 双链，配合 §3.2 的两条件执行定义，再接 Figure 3–7 的模型/信息/长度梯度；图让读者先看到可执行判定，再解释能力差异。[p. 2、4–8，`interpretation`]
5. **最大缺口**：最高层的 `34 zero-days` 与 `18 incomplete patches` 依赖人工 root-cause/dedup，逐案 PoC 因 disclosure 未公开；引言的 `17/10` 与 §5 的 `18/9` 也未调和，proxy 只以两模型的并置结果支持。[p. 2、9–11，`interpretation`]
6. **可迁移规则**：agent benchmark 的正文至少保留任务输入、可执行 success oracle、主要分母、一个成功机制 trace、关键异质性/失败诊断和现实外溢判定；长日志、全量配置和补充分层结果可移入附录，但正文需明确调用位置。[p. 4–10、19–46，`interpretation`]
7. **适用边界**：该规则适合拥有可信 pre/post execution oracle 的 reproduction 任务。对 logic flaw、exploitation、patch preservation、web/mobile 或人类评测，`no sanitizer crash` 不能直接充当同强度的 ground truth，需要另外定义有效性 oracle 和机制证据。[p. 4、10，`interpretation`]
