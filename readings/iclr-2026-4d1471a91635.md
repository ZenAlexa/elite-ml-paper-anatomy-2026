## 4. 闭环方法、形式化与训练数据流程

### 4.1 闭环的可执行链

World-In-World 的闭环不是只生成 rollout：每一步以当前 observation `o_t` 和目标 `g` 由 `π_proposal` 采样 `M` 个长度为 `L` 的候选动作序列；`C` 把候选转换为各模型需要的 text、camera trajectory 或 low-level action；`g_θ` 生成未来 observation；`π_revision` 根据 `(A_hat, O_hat)` 选择或合成 `D*_t`；将该决定在真实环境执行，取得 `o_(t+1)` 后重启循环。【p.3 Figure 3｜explicit｜“closes the interaction loop”】【p.4 §2.1｜explicit｜“policy-guided beam search”】【p.4 §2.2｜explicit｜“text prompt, camera trajectory/viewpoint”】

- **输入、状态和输出**：`o_t` 是 egocentric observation，`g` 是 task goal，`A_hat` 是候选未来动作，`I=C(A_hat)` 是模型控制输入，`O_hat` 是 counterfactual future observations，`D*_t` 是最终 decision。`D*_t` 可为 action sequence、recognition result 或 refined low-level action，故框架覆盖问答与控制，而不局限于传统 MPC 的动作序列优化。【p.3 §2.1｜explicit｜“observation may be RGB, RGB-D”】【p.4 §2.1｜explicit｜“more general than classical MPC”】
- **动作 API 的三个分支**：image-and-text-to-video 用模板把 primitive action 变成 `I_text`；viewpoint 模型用平移与方位变化得到相机轨迹；native-action 模型把 `A` 映射到各自 action vocabulary。后两项给出的实例尺度为平移 0.2 m、旋转 22.5°。【p.4 §2.2｜explicit｜“three principal types of control”】【p.5 §2.2｜explicit｜“changes the azimuth by 22.5”】
- **任务特定回收**：AR 用 imagined views 同时辅助识别与导航；ImageNav 和 manipulation 用于 plan selection；A-EQA 用高层计划的 terminal predicted observation 评估候选探索。这样，统一链在任务中保留 proposal–simulation–revision 的同一因果顺序。【p.20 §B.1｜explicit｜“supports both queries”】【p.21 §B.2｜explicit｜“exclusively for planning enhancement”】【p.22 §B.3｜explicit｜“only the terminal predicted observation”】【p.23 §B.4｜explicit｜“propose, simulate, and revise loop”】

方法段落转移可概括为：`state_problem → define_component → setup_notation → derive → define_component → explain_mechanism → connect_to_experiment`。Figure 3 承担系统图，Equations (1)–(4)依次承担候选采样、世界模型 rollout、revision 决策与 score-and-select 的形式化；这些式子描述接口，没有 theorem、lemma、proposition、corollary 或证明，因此属于 `core_chain` 的操作定义，不构成理论保证。【p.3 §2｜explicit｜“common interface across tasks and models”】【p.4 §2.1｜explicit｜Equations (1) to (4)】

### 4.2 训练与数据流程

- 对 Habitat-Sim 的 AR、A-EQA、ImageNav，作者从 HM3D training split 收集 panoramic action-observation 数据；对于 CoppeliaSim manipulation，从 RLBench demonstrations 收集数据。Habitat-Sim 的 post-training scene 与评测 scene 明示不重合，目标是区分 generalization 与 memorization。【p.6 §2.4｜explicit｜“scenes that are disjoint”】【p.27 §D｜explicit｜“200 demonstrations for each”】
- Appendix C 将目标写为在初始 RGB frame 与 `C(A)` 条件下学习 future-observation distribution；Habitat 使用 Forward、Turn_Left、Turn_Right、Stop 四个 discrete primitives，manipulation 使用连续 7-DoF end-effector poses。为了对齐 Habitat 中 action 与 frame，首帧加入 `a_Null`；manipulation 的 absolute pose 与 frame 天然一一对应。【p.26 §C.1｜explicit｜“one-to-one alignment”】【p.26 §C.2｜explicit｜“four navigation primitives”】
- 默认配置是每类任务 40K sampled instances、一个 epoch、从官方 pretrained weights 初始化；14B 变体采用 LoRA，其余模型 full-weight fine-tuning。Table 8 给出仓库、帧数与训练分辨率；Table 10 给出四个模型约 40K clips 的 H100 GPU-hours，说明成本在模型间并不相同。【p.27 §C.2｜explicit｜“40K sampled instances”】【p.27 §C.2｜explicit｜“adapted ... for one epoch”】【p.27 Table 10｜explicit｜“H100 GPU-hours”】
- Appendix D 的 Habitat dataset 构造是 waypoint selection、collision-free shortest-path generation 与动态 waypoint refresh 三阶段。Algorithm 1 的关键不变量是 retained waypoint 的最小 geodesic 间距 `r_f`，每段轨迹后移除半径内已访问点，再重算 leaf score 和未访问集；Table 11 报告 858 scenes、763,724 panorama RGB frames 和 439,213 action trajectories。【p.28 Algorithm 1｜explicit｜“Three-stage construction”】【p.29 §D.1｜explicit｜“avoiding redundant sampling”】【p.28 Table 11｜explicit｜“Number of scenes 858”】

### 7.2 作者明示的限制

1. **未见环境的 generalization**：web-video pretraining 可能让模型回到训练先验或忽略 action controls，造成 plausibly visual but physically/semantically inconsistent rollout。【p.10 §4｜explicit｜“revert to training priors”】
2. **长时域规划**：当前视觉 WMs 处理 short-term change 更可行，缺少累积 spatiotemporal history 的机制；把 front view 换为 panorama 的结果不一致。【p.10 §4｜explicit｜“struggle on long horizons”】【p.10 §4｜explicit｜“gains were inconsistent”】
3. **精确 interaction dynamics**：manipulation 需要接触、顺应性、摩擦和状态变化，当前 rollout 会违反物理并损害 control。【p.10 §4｜explicit｜“contact-rich interactions”】【p.10 §4｜explicit｜“violate physics”】
4. **proposal/revision policy 是性能下限**：WM fidelity 与 proposal/revision strength 共同决定总表现，强 base policy 会抬高上限。【p.10 §4｜explicit｜“set the performance floor”】
5. **计算成本**：每决策步的多个 future rollout 增加开销；实时或受限硬件场景可能无法承受。【p.10 §4｜explicit｜“strict real-time constraints”】
