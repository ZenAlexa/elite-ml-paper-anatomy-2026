## E. 方法与理论

### E.1 形式化对象和信息流

§2.1 将任务写为 `(R, q, E)`：repository state、自然语言问题和 evaluation oracle；每一步按历史 `h_{t−1}` 与 `q` 选择 action，再从 `Obs(a_t,R)` 得到 observation。动作示例是 search/read/edit/test，观察示例是 file contents、compiler errors、test results；典型流程是 `localize → read → edit → test → revise`。完整 trajectory 还带有 `y∈{0,1}` 的成功标签。[p.3, §2.1, “We formalize an agentic software engineering task as a tuple (R, q, E)”]

§2.2 的因果断点是：静态训练样本只呈现最终 code/commit，部署却要求模型构造一串 action–observation pairs；即使保留 workflow 结构，若没有失败、错误和 revision，模型仍需在 post-training 阶段才学习 feedback loop。[p.3–4, §2.2, “training data shows what was ultimately produced, but deployment requires agents to learn how to construct solutions”]

### E.2 数据方法的最小逻辑单元

方法动作序列为：

`setup_notation → state_problem → define_component → explain_mechanism → give_intuition → instantiate_algorithm（未使用伪代码，以数据管线实例化） → connect_to_experiment → summarize`。

| 单元 | 内容与前文问题的对应 | 页／证据 |
|---|---|---|
| 1. 设定两类轨迹 | §3 将 agent-native data 定义为保留完整 action–observation trajectory 与环境反馈的 supervision；宽度由 contextually-native、深度由 environmentally-native 补足。 | p.4, §3, “The combination ensures both breadth … and depth” |
| 2. Contextually-native 设计 | GitHub PR 同时连接 issue、代码变化和 validation signals；不把 localization 与 editing 分开，使编辑决定条件于定位时收集的 context。 | p.4, §3.1.1, “bundling complete context” |
| 3. Contextually-native 采集 | `Dgen^ctx` 来自 top 10,000 starred repositories、跨语言；`Dpy^ctx` 来自至少 5 stars、未 archived、Python-focused repositories，两个子集在 Python 上部分重叠但目标不同。 | p.4–5, §3.1.2, “The two subsets partially overlap in Python repositories but serve complementary purposes” |
| 4. 过滤和对齐 | 只保留 merged、非 bot PR；Python 子集再限改动为 Python source/documentation、1–5 个 Python 文件；内容和 patch 对齐到 first PR commit 的 parent，而不是可能失真的 PR metadata base。 | p.5, §3.1.2, “align file contents and patches with the parent of the first PR commit” |
| 5. Reconstruction | 先用 Qwen3-235B-A22B-Instruct-2507 生成 PR summary 和 refined commit messages，再确定 symmetric diff 的 modified files、取 base contents，最后按 Repository Context→Issue→Files→Summary→Edits 组织。 | p.5, §3.1.2, “Template organization” |
| 6. 两种格式 | `Dgen^ctx` 用 XML-like tags、patch diffs、comments/reviews；`Dpy^ctx` 用 Markdown、search-and-replace blocks；多 commit 按时间串接。 | p.5, §3.1.2, “The two subsets use different structural formats” |
| 7. 规模与去污染 | 长度超过 32k tokens 的 sample 丢弃；超过 90% Python PR 保留；移除 SWE-Bench Verified 所在 repositories。最终 Dgen=26.7B、Dpy=41.9B、Dctx=68.6B。 | p.5–6, §3.1.3, “Dctx … contains 68.6B tokens” |
| 8. Environmentally-native 设计 | 真实 Docker 环境记录 file/tool/test/error 的观察，解决 contextually-native 只有结构、没有真实 edit→test→revise dynamics 的缺口。 | p.6, §3.2.1, “actual agent-environment interactions” |
| 9. Environment rollout | 从真实 GitHub PR 构建 Docker、unit tests 和 tool-call infrastructure；SWE-AGENT 中部署 GLM-4.6，每个 task 最多 4 rollouts；按最终 tests 分为 passing 与 non-passing。 | p.6, §3.2.2, “For each task, we generate up to 4 rollouts” |
| 10. 轨迹统计与训练接点 | 得到 `Dpass^env` 1.85×10⁴/0.7B、`Dfail^env` 5.55×10⁴/2.4B，共约 7.4×10⁴ trajectories、3.1B tokens；后续训练将 passing 子集上采样 3×。 | p.6、p.7, §3.2.3/§4.2, “We upsample Dpass^env by 3× during training” |

### E.3 方程、理论结果和算法

全文只有 3 个 displayed equations，均无编号：

1. **动作选择**：`a_t ∼ π_θ(a | h_{t−1}, q)`，p.3 §2.1；定义 agent 如何依赖历史和问题选 action。[p.3, §2.1, “action selection”]
2. **观察生成**：`o_t ∼ Obs(a_t, R)`，p.3 §2.1；定义环境从 action 和 repository state 产生 observation。[p.3, §2.1, “observation”]
3. **去污染比率**：`leakage_ratio(e,x)=|G_e∩G_x|/|G_e|`，p.15 Appendix D；按 13-gram 集合重叠定义 benchmark instance 的泄漏比率。[p.15, Appendix D, “Similarity is measured as a leakage ratio”]

## H. 消融、负面结果与自我设限

### H.1 消融对象和识别目标

Table 4 占 p.9 的中部，正文约一小段；它有两个识别目标：

1. **组件删除／组合**：`Denv` vs `Denv + Dpyctx` 的 zero-shot 对比，识别 PR grounding 是否为 executable trajectories 提供必要的 code/context prior。
2. **MT→SFT double-dipping**：固定 downstream `Dpass` 时比较只有 `Dpyctx`、`Denv+Dpyctx`、完整 `Denv+Dctx`，识别 trajectory 在 MT 的额外初始化价值和 contextually-native 规模价值。

表 4 没有逐个删除 summary、commit-message refinement、reviews、test feedback 或格式标签；没有超参数敏感性、task heterogeneity、失败案例或 compute ablation。因而它支持“数据组合”的机制解释，不支持每个管线组件的独立必要性。[p.9, Table 4, “Ablation of data components in MT”]

4. **实验报告缺口（版面事实）**：正文／附录未给 seed、硬件、训练时长、FLOPs、货币成本、task-level error bars、跨 family evaluation、human/deployment evaluation；这是报告粒度缺口，不把它改写成作者明示的限制。[p.6–7、p.15, §§4.1–4.2/Appendix A.2；layout observation]

## L. 最终判断

1. **单一主线**：把 agentic SWE 的训练目标从“独立技能或最终 patch”改为保留完整信息流的 agent-native mid-training；`Dctx` 提供跨仓库、跨语言的 context breadth，`Denv` 提供真实执行 feedback depth，二者共同改善后续 agentic SFT。
2. **正文保留的决策关键内容**：任务形式化、localize→read→edit→test→revise loop、两类数据定义与规模、SWE-AGENT/模型设定、Table 1–4、Figure 4、单 benchmark/family 与 patched evaluator 限制。这使“数据结构→execution dynamics→性能”的核心判断可在正文内追踪。
3. **移入附录的细节及影响**：staging、batch/LR/mask、LLM prompts、General/Python format、13-gram 去污染规则和 24 个被移除实例在附录。迁移有利于压缩正文，但训练和评测复现不能只读正文；附录未提供理论证明、额外主结果或更细组件消融。
4. **最有效模式**：Figure 2 先用四格图把 factorization 的 train-test mismatch 与两种 agent-native data 的角色可视化；Table 1 用同一 SWE-AGENT/相近 base 组织 weak/strong SFT、32B/72B；Table 4 再把“PR grounding”和“MT trajectory value”拆成两个局部对比。图表都由紧邻正文段落解释，图注承担补充说明。[p.4、p.7、p.9]
5. **最明显缺口**：没有与“同一格式但去掉真实 execution feedback”的严格控制，没有按 summary/review/commit order/test feedback 拆开的组件消融，也没有 seed/hardware/成本/task-level uncertainty。`state-of-the-art` 和“not saturated”分别受 Table 2 条件异质、Figure 4 单区间拟合限制。[p.6–10]
6. **可迁移规则**：当研究主张的是 agentic workflow 时，训练样本应把决策前的 context、动作、真实 observation 和 revision 放在同一可追踪链中；正文应同时给一个结构对照（为何 factorization 失配）和一个最小成分消融（哪种信息源改变结果）。
7. **适用边界**：该规则适用于有可观测工具调用／环境反馈、且部署需要长程状态更新的代码或工具使用任务；若任务是单轮、上下文已完整给定，或不存在可验证的 execution oracle，`contextually-native`／`environmentally-native` 的区分不能直接推出同样的收益。[p.3、p.6, §§2.1/3.2]

**证据覆盖**：本备忘的实质判断均附物理页码、章节和不超过 20 个英文词的证据锚点或图／表／公式编号；缺失信息保留为 `not_present`，未把开放计划或拟合趋势写成已完成事实。
