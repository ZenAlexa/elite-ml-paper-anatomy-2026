## 跨对象系统判断

- **视觉叙事**：Figure 1 先定义 Home–Agent–Server/Matter 接口，Figure 2 展示 episode 生成，Figure 3 固定 simulator 与 LLM judge 的评估合同；Tables 1–2 给出全模型成功率与时间，Table 3、Figure 4、Figure 5 将失败类型和即时反馈恢复展开；Appendix Tables 4–7 补齐 API/device/cluster/goal schema，Tables 8–11 补错误定义/计数，Figure 6 与 Tables 12–14 做 framework、feedback 和 SFT 消融。整体路径是接口→生成→评估→能力/成本→失败机制→附录复现→干预边界。
- **Caption 系统**：所有 caption 使用 “Figure/Table N:” 加普通 serif 说明句，未观察到粗体结论式标题。Figure 1–3 说明流程/评估设置，Table 1 明确定义 F/IF 与 S/J、best/second-best，Figure 5 说明两个 panel 的分母，Table 13/14 显式交代 oracle 或 absolute-score 指针；多数 caption 不给样本数、区间或主结果方向，主发现留在正文。
- **表头系统**：主文 Table 1/2 与附录 Table 14 采用两级 QT→F/IF 表头；Table 1 另用四个 model-family row groups。其余表使用扁平列头，T3/T8/T9 以定义类文本，T4–T7 以 API/device/cluster/query contract，T10–T13 以 count/recovery 数值。宽表和 longtable 重复表头，黑白 booktabs/partial-grid 贯穿。
- **方法—结果—消融链**：Figure 1 的 Matter/tool interface → Figure 2 的随机状态与 goal/query 生产 → Figure 3 的双 evaluator → Table 1/2 主结果与成本 → Table 3/Figure 4/Table 10–11 错误构成 → Figure 5 即时反馈恢复 → Figure 6 framework、Table 12 self-review、Table 13 oracle notice、Table 14 SFT。该链条把“能力差异”“反馈条件”和“部署代价”分开但仍可回链。
- **正文—附录链**：正文 Figure 3 与 Table 3/Figure 4/5 调用 Appendix A–J 的接口、goal、judge 与错误细节；Appendix M/O/P 的 Figure 6 与 Tables 12–14 对正文 framework、feedback、SFT 讨论提供切片。T6/T7 跨页重复表头，保证大部分复现 schema 可脱离正文检查，但参数和 prompt 仍需回看对应 section。
- **字体一致性**：外部 captions、正文、表头和表值主要使用 Nimbus Roman No9 L/Computer Modern，工具名和 API 参数使用 NimbusMonL/Courier-like 等宽体；流程图/chart 内部使用 Arial/Freesentation/DejaVu Sans。表格字号在宽表和附录 longtable 中压缩，保持了规则一致但牺牲了小屏可读性。
- **颜色一致性**：蓝色反复表示 agent/process 或 successful/first-try，绿色表示 environment response/success，橙色表示 commands/alternative framework，灰色表示背景/中性流程；Figure 4 的类别色和 Figure 5 的粉色是局部语义。直接文字、状态符号和柱内数值提供冗余，但颜色仍是大多数比较的主要通道，灰度安全性弱。

## 最终判断

- **最可复用模式**：
  - 用 Figure 1 的状态—接口—反馈架构定义可执行 benchmark 边界，并让 Figure 2/3 分别承接生成与评估合同。
  - 用 QT→F/IF（以及 S/J evaluator）两级表头把任务条件和测量协议绑定在同一能力矩阵中。
  - 用 taxonomy 表→直接标注 pie small multiples→绝对 count 表的三步错误分析，分离定义、比例和分母。
  - 用 Figure 5 的调用级 stacked bars 加 episode recovery composition，同时报告错误发生量和恢复结果；用 repeated-header longtable 公开复现 schema。
- **最高价值对象**：
  - Figure 3：最清楚地固定 simulator assertion 与 LLM judge 的评估契约。
  - Table 1：六类 QT、F/IF 和两种 evaluator 的中心能力矩阵。
  - Figure 5：把即时 tool feedback 变成可观察的错误调用与 recovery 机制。
  - Figure 1：将 Matter API、设备状态和 environment response 连接为接口锚点；Table 2 补充真实部署相关的延迟代价。
- **主要失败模式**：
  - 宽表（尤其 Table 1/14）列密度高，许多对象缺少 episode 分母、重复、区间或误差显示。
  - Figure 4 的缩写和饼图比较依赖 Table 3，类别角度难以精确横向比较；Figure 1–3 的栅格流程图小字在缩放后受限。
  - 蓝/橙/绿/粉的语义大多没有形状或线型的完整冗余，灰度和色觉异常场景可读性有限。
  - 公开仓库没有最终图表生成脚本或 exact source，且相关 rendered assets 与 PDF 最终标签/布局不同；model family、prompt、serving 和 feedback 条件也限制机制归因。
- **一句话视觉策略**：以 Home–Agent–Server 架构和 episode/evaluation 流程建立可执行接口，再用多层 query 成功率、延迟、错误构成与反馈恢复逐步定位 QT4 瓶颈，最后以附录 API、设备/cluster、goal 与 ablation 表补齐复现边界。
